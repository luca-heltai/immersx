# PLAN.md

## Objective

Extend the current VTK-based reduced coupling workflow so that scalar or component-wise VTK fields can be exposed as symbolic variables and used in parameter-file expressions.

The main target use cases are:

```text
Input file fields = radius, hematocrit
Reduced right hand side = radius^2 + 5; hematocrit * radius
Thickness expression = radius
```

The implementation must use deal.II's SymEngine integration rather than Python or SymPy.

The first implementation scope is limited to:

- discovering and cataloguing VTK `PointData` and `CellData` arrays;
- exposing selected arrays or components as symbolic variables;
- parsing and evaluating symbolic expressions with deal.II/SymEngine;
- using those expressions in the reduced right-hand side;
- using symbolic expressions for radius/thickness-dependent quantities;
- preserving legacy behavior when no symbolic VTK fields are requested;
- producing clear diagnostics for unsupported or inconsistent inputs;
- remaining robust under MPI and mesh refinement constraints.

Boundary-condition support is explicitly out of scope for this plan.

---

## Current State

The repository already contains most of the raw VTK data path:

- `VTKUtils::read_vtk()` reads both `PointData` and `CellData`;
- point data are represented with `FE_Q(1)`;
- cell data are represented with `FE_DGQ(0)`;
- field coefficients are stored in `properties`;
- field names are stored in `properties_names`;
- `TensorProductSpace` stores the associated `DoFHandler`, vectors, and names.

The missing layer is the connection between:

```text
VTK field name
  -> VTK association and component
  -> FE component
  -> value at a quadrature point
  -> SymEngine symbol
  -> evaluated expression
  -> assembly contribution
```

The current reduced right-hand side parser only knows coordinates, time, and constants. It cannot consume VTK field values.

There is also an existing design bug: `thickness_field_name` is duplicated across parameter structures. Different assembly paths can therefore consult different values. This must be fixed before extending the feature.

---

## Design Principles

1. Parse symbolic expressions exactly once during initialization.
2. Resolve all field names and components exactly once during initialization.
3. Perform no string lookup in cell or quadrature loops.
4. Keep VTK discovery, field binding, FE extraction, and symbolic evaluation as separate modules.
5. Treat all SymEngine variables as scalar.
6. Expand vector-valued VTK arrays into explicit scalar components.
7. Never silently select an ambiguous field.
8. Never silently replace missing fields with zero.
9. Keep legacy behavior available when symbolic VTK fields are not requested.
10. Compile cleanly both with and without `DEAL_II_WITH_SYMENGINE`.
11. Prefer small, independently reviewable pull requests.
12. Every work package must include its own tests.

## Proposed Core Data Structures

### VTK field catalogue

```cpp
enum class VTKFieldAssociation
{
  point_data,
  cell_data
};

struct VTKFieldDescriptor
{
  std::string         vtk_name;
  VTKFieldAssociation association;

  unsigned int n_components;
  unsigned int first_fe_component;
  unsigned int block_index;
};
```

The catalogue must be generated by the same scan that constructs the mixed finite element and imports VTK coefficients. There must not be two independent scans with potentially different ordering.

### Symbol binding

```cpp
struct InputFieldBinding
{
  std::string  symbol_name;
  unsigned int field_index;
  unsigned int vtk_component;
  unsigned int fe_component;
};
```

Each binding maps one scalar symbolic variable to one scalar FE component.

Examples:

```text
radius      -> field "radius", component 0
hct         -> field "hematocrit", component 0
velocity_0  -> field "velocity", component 0
velocity_1  -> field "velocity", component 1
```

## Parameter File Contract

Recommended syntax:

```text
subsection Tensor product coupling
  subsection Representative domain
    set Reduced grid name = vessels.vtk

    set Input file fields = radius, hematocrit

    set Thickness expression = radius

    set Reduced right hand side = \
      radius^2 + 5;               \
      hematocrit * radius;        \
      0
  end
end
```

### `Input file fields`

Supported forms:

```text
radius
hct=hematocrit
ux=velocity[0]
radius_cell=cell:radius
radius_point=point:radius
*
```

Semantics:

- empty value: expose no VTK fields;
- `*`: expose every valid scalar field and every component of vector fields;
- `radius`: expose an unambiguous scalar array with the same name;
- `hct=hematocrit`: expose `hematocrit` as symbolic variable `hct`;
- `ux=velocity[0]`: expose component zero of `velocity` as `ux`;
- `point:` and `cell:` disambiguate equal names in `PointData` and `CellData`.

Reserved names must include at least:

```text
x, y, z, t, pi
```

and all constants already registered by the application.

Vector fields imported through `*` must use deterministic names:

```text
velocity_0
velocity_1
velocity_2
```

Do not generate `_x`, `_y`, or `_z` automatically because a three-component VTK array is not necessarily Cartesian.

### `Thickness expression`

Precedence:

1. use `Thickness expression` when non-empty;
2. otherwise convert the legacy `Thickness field name` to the equivalent single-symbol expression;
3. otherwise use the constant `Thickness` value.

Time-dependent thickness expressions are out of scope for the initial implementation. Reject use of `t` in `Thickness expression` with a clear error.

### Error policy

Initialization must fail for:

- requested field not present;
- ambiguous field name;
- invalid component index;
- invalid symbolic identifier;
- duplicate symbolic alias;
- reserved symbolic name;
- unknown free symbol in an expression;
- wrong number of reduced RHS expressions;
- unsupported symbolic feature in builds without SymEngine.

## Symbolic Evaluation Architecture

Use deal.II's SymEngine integration:

- `Differentiation::SD::Expression` for parsed expressions;
- symbolic variables for coordinates, time, constants, and input fields;
- `Differentiation::SD::BatchOptimizer` for repeated evaluation of all expressions.

Do not update a `Functions::SymbolicFunction` substitution map at every quadrature point. VTK values vary pointwise, so the lower-level symbolic differentiation interfaces are a better fit.

Suggested interface:

```cpp
class SymbolicFieldEvaluator
{
public:
  void
  initialize(const std::vector<std::string> &expression_strings,
             const std::vector<std::string> &field_symbols,
             const std::map<std::string, double> &constants);

  unsigned int
  n_outputs() const;

  void
  evaluate(const Point<spacedim>         &point,
           double                         time,
           ArrayView<const double>        field_values,
           ArrayView<double>              output_values) const;
};
```

The evaluator must:

1. create all symbols once;
2. parse all expressions once;
3. validate free symbols once;
4. register all expressions in one optimizer;
5. optimize once;
6. accept only numeric values during assembly;
7. reject non-finite outputs with contextual diagnostics.

Thread safety must be verified explicitly. If the optimizer is not safely reusable across threads, each scratch object must own its own evaluator state.

---

## Initialization Order

The final initialization order must be:

```text
1. Read reduced triangulation.
2. Read VTK PointData and CellData.
3. Build the VTK field catalogue.
4. Resolve Input file fields into scalar bindings.
5. Initialize the thickness expression.
6. Compute geometric points, radii, measures, and weights.
7. Initialize the cross-section problem and selected basis functions.
8. Initialize reduced RHS symbolic expressions.
9. Build matrices and vectors.
```

The reduced RHS evaluator cannot be initialized before both the VTK bindings and the number of selected basis functions are known.

# Definition of Done

The feature is complete when all of the following are true:

1. A scalar VTK field can be used directly in a symbolic expression.
2. A selected component of a vector VTK field can be used through an alias.
3. `PointData` and `CellData` preserve their intended FE semantics.
4. Expressions are parsed and optimized once.
5. No field-name lookup occurs in quadrature loops.
6. Missing or ambiguous fields fail during initialization.
7. The reduced RHS expression count is checked against the selected basis count.
8. Legacy constant and coordinate-only expressions continue to work.
9. Legacy `Thickness field name` remains temporarily supported through translation to `Thickness expression`.
10. Builds without SymEngine fail only when the new symbolic functionality is requested, with a clear message.
11. Serial and MPI results are consistent.
12. Refinement cannot silently invalidate or zero imported properties.
13. Documentation covers grammar, examples, limitations, and migration.
14. Boundary-condition support has not been added as part of this effort.
